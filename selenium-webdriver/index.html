Web UI testing with Selenium WebDriver and pytest

You will install Selenium for Python, automate a small web form, and check expected results with pytest. The first script has a single test. The second adds the pytest features a real test suite needs: shared fixtures, helper functions, parametrized tests, assertion messages and expected errors.

  • Tools Python 3 · VS Code · Edge or Chrome
  • Libraries Selenium WebDriver · pytest
  • Time about 60–90 minutes

Who this tutorial is for

Undergraduate software engineering students who can write basic Python and want to automate tests for a web user interface. You will learn to turn a written test case into an automated one, and to keep a growing suite of UI tests fast, readable and reliable.

What is Selenium WebDriver

Selenium is an open-source project for automating web browsers. Selenium WebDriver lets Python control a real browser: open a page, find an element, type, click, and read what the page displays. A browser driver connects WebDriver to Edge or Chrome; Selenium Manager, which ships with Selenium, usually finds or downloads that driver for you.

What you will have at the end

  • A one-test script that automates a documented test case step by step
  • A 14-test suite that uses fixtures, helpers, parametrized rows and expected exceptions
  • A repeatable way to apply the same pattern to any web application you need to test

STEP 1Set up the project

Goal: a project folder with its own virtual environment and Selenium and pytest installed.

What you need

  • Python 3 and VS Code. Check Python with python --version on Windows or python3 --version on macOS and Linux.
  • Microsoft Edge or Google Chrome, and an internet connection. The examples use Edge, which is preinstalled on Windows; each code block notes the one-word change for Chrome.
  • No administrator access is needed: packages go into a project virtual environment. On the first run, Selenium Manager may need network access to locate or download a matching browser driver.

STEP 2Define the first test case

Goal: a written test case to automate, so the code has something to be checked against.

The application under test is the Selenium project's sample web form at selenium.dev/selenium/web/web-form.html. It is a practice page built for exactly this purpose. Open it once in your browser and look around.

Good automated tests start as written test cases. Writing the steps and the expected result first means the script checks what the application should do, not whatever it happens to do.

STEP 3Write the first automated test

Goal: one pytest test that performs FORM-01 step by step.

Create test_web_form.py in the selenium-lab folder and copy this script into it. pytest recognizes files named test_*.py and functions named test_*. Each comment matches a step of the test case.

Every piece of pytest and Selenium syntax in the script:

  • import pytest and the from selenium ... lines load the two libraries. By names locator strategies; WebDriverWait and EC (expected conditions) wait for the page.
  • @pytest.fixture above def driver() marks a setup function. A test receives the fixture's value by listing the fixture name as a parameter: def test_form_01_submit_text(driver).
  • yield browser hands the browser to the test and pauses the fixture. When the test ends, pytest resumes after the yield and runs browser.quit(), even if the test failed.
  • driver.get(url) opens a page. find_element(By.NAME, "my-text") finds one element by its HTML name; By.ID and By.CSS_SELECTOR are other strategies. send_keys types and click presses.
  • wait.until(EC.visibility_of_element_located(locator)) waits up to 10 seconds for the element to appear, then returns it. Use waits instead of time.sleep so tests are fast and stable.
  • assert actual == expected compares what the page shows with what the test case expects. A false assertion fails the test and pytest reports the difference.

Copying code

Use the Copy button and keep the indentation at four spaces per level. Python treats indentation as part of the syntax.

A test you have never seen fail might not be checking anything. Breaking the expected value on purpose proves the assertion runs and that a real difference would be reported.

STEP 5Find good locators

Goal: name every locator once, and read its value from the page's HTML.

One test is easy; a suite of many tests would repeat the browser setup, the page load and the steps in every function. Steps 5 to 8 build a second file, test_web_form_pytest.py, one piece at a time. Each piece adds some pytest or Selenium syntax, and the complete file is listed at the end of Step 8. Create the file now and add each block as you read.

5a · Name URLs and locators once

A locator is a pair: (By.<strategy>, value). Storing it in a constant such as TEXT_BOX keeps the page detail in one place; if the page changes, you edit one line. Four strategies cover most pages:

StrategyMatchesUse it when
By.IDThe element's id attributeAn id exists. It is the most reliable choice.
By.NAMEThe name attributeForm fields, which usually have one
By.CSS_SELECTORCSS syntax, such as input[name='my-disabled'] or #my-check-2You need to combine a tag with an attribute
By.XPATHA path through the page, such as //button[normalize-space(.)='Submit']A control has no id or name, and only its visible text identifies it

5b · Find the value for a locator

The value in each pair comes from the page's HTML, which you read with the browser's developer tools. Repeat these steps for every control your tests touch:

  1. Inspect the control. Open the form in Edge or Chrome, right-click the Text input box, and choose Inspect. The Elements panel opens with the box's HTML tag highlighted. Hovering over a tag in the panel highlights the matching control on the page, which confirms you are looking at the right element.
  2. Read the tag. The highlighted line for the Text input box is:
  1. Pick an attribute and copy its value exactly, including case and hyphens. The tag has id="my-text-id", so (By.ID, "my-text-id") works, and it has name="my-text", so (By.NAME, "my-text") works too; the script uses the second. Values such as class="form-control" are shared by many controls, so they do not identify one element.
  2. If the tag has no id or name, build a CSS selector or an XPath from what it does have: the tag name, another attribute, or its visible text. The other locators in the script were read from these tags:
ControlWhat the tag offersLocator in the script
Disabled inputname="my-disabled"(By.CSS_SELECTOR, "input[name='my-disabled']")
Default checkboxid="my-check-2"; the name my-check is shared by two boxes(By.ID, "my-check-2")
Dropdownname="my-select"(By.NAME, "my-select")
Submit buttonNo id or name, only the text Submit(By.XPATH, "//button[normalize-space(.)='Submit']")
Confirmation messageid="message" on the result page(By.ID, "message")

Check a locator before you use it

  • It matches exactly one element. In the Elements panel press Ctrl+F (⌘+F on macOS) and paste the CSS selector or XPath; the search box should report "1 of 1". A locator that matches several elements returns the first one, which is usually not the one you meant.
  • It survives layout changes. The right-click Copy → Copy selector and Copy XPath commands produce paths such as #main > div:nth-child(3) > button that break as soon as the layout changes. Prefer a short value based on an id, a name or visible text.

The Submit button's relative XPath, //button[normalize-space(.)='Submit'], reads as follows:

  • //button: any button element, anywhere on the page.
  • normalize-space(.): the button's text, with leading and trailing spaces removed and inner whitespace collapsed.
  • ='Submit': keep only buttons whose normalized text is exactly "Submit".

STEP 6Share setup with fixtures and helpers

Goal: one browser for the whole file, a fresh page for every test, and the repeated steps in one function.

6a · Share one browser with a module-scoped fixture

The first script started a new browser for every test. With scope="module" the fixture runs once per file: the browser starts before the first test and quits after the last one, which is much faster for a suite of many tests. The try/finally guarantees driver.quit() runs even if a test crashes. Without a scope argument, the default scope="function" runs the fixture again for every test.

EdgeOptions configures the browser before it starts. --headless=new runs it without a window, which is convenient for repeated runs; remove that line to watch the tests. --window-size gives the page a fixed size, so elements are laid out the same way on every run. Chrome users replace EdgeOptions with ChromeOptions and Edge with Chrome.

6b · Chain fixtures so every test starts from a known state

A fixture may request another fixture by naming it as a parameter, so form receives the shared browser. Because form has the default function scope, it runs before each test that asks for it: it reloads the page, waits for the text box, and returns the browser. Each test that takes form as its parameter begins on a fresh page and cannot be affected by what an earlier test typed or clicked.

Test independence

Every test should pass whether it runs alone, first, last or in any order. Sharing an expensive resource (the browser) while resetting cheap state (the page) for every test gives you speed without hidden dependencies between tests.

6c · Move repeated steps into helper functions

pytest only collects functions whose names start with test_, so submit_text is an ordinary helper. It performs the steps of a test case (type, click Submit, wait for the message) and returns the value the test needs to check. The test then reads like a test case: perform the action, then compare actual with expected.

  • EC.element_to_be_clickable waits until the button is visible and enabled. Because wait.until returns the element, .click() can be chained onto it.
  • .text reads the text displayed inside an element.
  • * is Python's argument-unpacking operator. Because TEXT_BOX = (By.NAME, "my-text"), the call find_element(*TEXT_BOX) is expanded to find_element(By.NAME, "my-text").

STEP 7Run one test with many inputs

Goal: cover several inputs with one function, and make each failure explain itself.

7a · Parametrize

@pytest.mark.parametrize repeats a test once for each row in the list. The first argument is a string naming the parameters, and those names must appear in the test function's parameter list. test_form_03 has one parameter, text, and three values, so pytest creates three tests.

test_form_04 shows the form you will use most: two parameters, text and expected_query, with each row wrapped in pytest.param(..., id="..."). The id replaces the raw values in the test name, so the output reads test_form_04_submitted_text_is_in_url[space-becomes-plus]. Choose ids that name the condition being tested.

This form sends its values in the page address after Submit, so form.current_url is a second place to check the result. The empty-text row shows that a parametrized test can cover boundary inputs with no extra code.

Traceability

One written test case becomes one test function or one parametrized row. Either way, its name in the pytest output should let a reader find the matching test case in your test plan, for example by including its ID.

7b · Explain failures with assertion messages

assert condition, message attaches a message that pytest prints when the assertion fails. Build it with an f-string so it names the input and the actual value; !r prints the value with quotes, which makes an empty string or a stray space visible.

The message Three: got '3' tells you which input failed without opening the code. The other rows of the same parametrized test still pass, which is why one row per test case is useful: a single wrong expectation does not hide the results of the others.

STEP 8Test more controls and expected errors

Goal: work with dropdowns, checkboxes and field values, and test that the page refuses invalid actions.

8a · Dropdowns, checkboxes and field values

  • Select wraps an HTML dropdown. select_by_visible_text("Two") picks an option by its label, select_by_value("2") by its value attribute, and first_selected_option returns the chosen option element.
  • is_selected() reports whether a checkbox or radio button is checked; click() toggles it. is_displayed() and is_enabled() are the other two state checks.
  • .text returns the text displayed inside an element such as a heading, label or result panel. What a user typed into an input box is not text: read it with get_attribute("value"). clear() empties an input box.
  • Each of these tests asserts more than once. pytest stops a test at its first failing assertion, so put the most basic check first.

8b · Test error handling with expected errors

Requirements about error handling take two forms in a test:

  • The application shows a message, for example "Error" or "Invalid input". Read the message element and assert its .text, exactly as test_form_02 asserts "Received!".
  • The application refuses the action, and Selenium raises an exception. with pytest.raises(...) makes that the expected outcome: the test passes only if the code inside the with block raises the named exception, and fails if nothing is raised. Typing into a disabled field raises ElementNotInteractableException, imported from selenium.common.exceptions at the top of the file.

Negative tests

Testing only the happy path leaves half the requirements unchecked. For every input a user can get wrong, plan at least one test that confirms the application rejects it clearly.

8c · Let the file run itself

With this block at the bottom, the file can also be run with the VS Code Run button or with python test_web_form_pytest.py. pytest.main runs pytest on this file only and returns its exit code, which SystemExit passes on to the terminal. python -m pytest still works and is the normal way to run the whole suite.

8d · The complete second script

Your test_web_form_pytest.py should now match this listing. Compare it with yours if a test does not run.

The pytest syntax in this tutorial, in one place

SyntaxWhat it does
def test_name(...) in a file named test_*.pyA test. pytest collects it automatically; other functions are helpers.
assert actual == expected, messageChecks a result. A false condition fails the test and prints the message and the difference.
@pytest.fixture above a functionSetup code. A test or another fixture receives its value by naming it as a parameter.
yield value inside a fixtureGives the value to the test; the code after yield runs as cleanup when the test ends.
@pytest.fixture(scope="module")Runs the fixture once per file instead of once per test.
@pytest.mark.parametrize("a, b", [rows])Repeats the test once per row, passing the row values as parameters a and b.
pytest.param(values, id="name")One row of a parametrize list, with a readable name shown in the output.
with pytest.raises(SomeException):Passes only if the block raises that exception; fails if it does not.
pytest.main([__file__, "-v"])Runs pytest from inside the script, so the file can be run directly.

Keep evidence of each run

A test report should show which tests ran and what happened, so anyone can check a result later. Run the complete suite with -v and keep the output: save it to a text file, or write a JUnit XML report, which CI servers and test-management tools can read.

STEP 10Apply the pattern to your own application

Goal: a repeatable process for testing any web application, not just the sample form.

  1. Write the test cases before you look at the implementation. Derive each test case's input, steps and expected result from the requirements. Tests written by watching what the application does tend to accept its defects as correct behaviour.
  2. Then find the locators. Open the application and use Inspect to find reliable locators for its controls and its result display. Do not assume the sample form's locators apply to another page.
  3. Map test cases to tests one to one. Create one test function, or one parametrized row, per written test case, with the test case ID recognizable in the function name or the pytest.param id. Keep the documented input, steps and expected result aligned with the code.
  4. Start every test from a known state. Use a module-scoped browser fixture and a function-scoped fixture that reloads the page or resets the application. Put repeated steps in helper functions that return the displayed result.
  5. Test through the user interface. Enter input through the page controls, read the result the page displays, and assert the value the test case expects. Never compute the expected value in Python inside the test: if the test uses the same logic as the application, it will repeat the application's mistakes. Use waits wherever the result updates asynchronously.
  6. Treat a failure as information. When a test fails because the application is wrong, do not change the expectation to make it pass. Record the actual result, report the defect, and keep the expectation tied to the requirement.
  7. Run the whole suite often with python -m pytest -v, and keep the results so each automated test can be traced to its test case and each failure to a defect report.

Using AI coding tools to write Selenium tests

AI assistants can draft Selenium tests quickly, but they do not know your requirements. Give them the exact test cases with their steps and expected results, then review every generated test against those test cases: check the locators in the browser, check that each assertion matches the documented expected result, and see each test fail once. Edit whatever does not match. You are responsible for the tests you keep.

Troubleshooting

SymptomLikely cause and fix
ModuleNotFoundErrorpytest is running with a different Python. Run it with the .venv Python as shown above, and check that pip show selenium pytest succeeds for that interpreter.
Browser does not launchUpdate Edge or Chrome, confirm it opens normally, and check network access for Selenium Manager on the first run. Match webdriver.Edge() or webdriver.Chrome() to the installed browser.
NoSuchElementException or TimeoutExceptionInspect the current page and the locator: check that the page loaded, the intended element exists, and the wait condition fits the behaviour. Avoid arbitrary time.sleep delays.
No tests ran, or fewer than expectedName the file with a test_ prefix, run pytest from the folder that contains it, and use --collect-only to list what pytest found. Each parametrized row counts as one test.
fixture 'form' not foundThe parameter name in the test must match a fixture function name exactly, and the fixture must be in the same file (or in a conftest.py).
SyntaxError or IndentationError after copying codeRe-indent with spaces only, and replace curly quotes with straight quotes.
StaleElementReferenceExceptionThe element was found before the page changed. Find it again after a click or page load instead of reusing the old variable.
ElementClickInterceptedException, or a click that does nothingWait with EC.element_to_be_clickable, set a window size, or scroll the element into view.
Tests pass alone but fail togetherWith a module-scoped browser, an earlier test left state behind. Make the per-test fixture reload the page or reset the application.
A headless run fails but a visible run passesAdd driver.save_screenshot("fail.png") before the failing assertion and open the image to see what the browser showed.
