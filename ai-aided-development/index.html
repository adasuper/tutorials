AI-aided software development, from spec to deployment

You will build and ship a small web app, TaskTrack, using GitHub Copilot in VS Code for every stage: requirements, code, tests, a Docker image and a GitLab CI/CD pipeline. The AI drafts. You decide, verify and own the result.

Who this tutorial is for

This tutorial is written for undergraduate software engineering students. Its aim is to teach you how to use AI tools properly and responsibly throughout software development: not as a shortcut that writes the project for you, but as an assistant whose every suggestion you review, test and take responsibility for.

  • Properly means giving the AI clear context and constraints, checking its output against a specification, and catching the mistakes it typically makes.
  • Responsibly means staying the author of your code, protecting secrets and private data, verifying dependencies, respecting licences, and following your course's academic integrity policy.

Each step pairs an AI-generated draft with a human review gate, so you practise the judgment that employers and instructors expect from an engineer who uses AI tools.

What you should already know

The software life cycle, Git basics (commit, branch, push), what a CI/CD pipeline does, how to build and run a Docker container, and why we write automated tests. Basic Python is enough: FastAPI and Pydantic are introduced as you go, and the small browser frontend is plain HTML and JavaScript you only need to review. Reading the generated code carefully is part of the exercise.

What you will have at the end

  • A GitLab repository with user stories, an architect-level SPEC.md, source code, tests traced to every acceptance criterion, a Dockerfile and .gitlab-ci.yml
  • A pipeline that lints, tests, builds and pushes a container image on every push to main
  • A running public deployment you can open in a browser
  • A PROMPTS.md log showing what the AI produced and what you changed

How to read the code in this tutorial

Copilot's output is not deterministic: you and your classmates will get different code from the same prompt. Every file shown here is a reference solution that has been run and passes its tests. Compare it with what Copilot gives you, and treat the differences as review material.

The workflow

AI-aided development follows the same life cycle you already know. What changes is who writes the first draft of each artifact. Every stage ends in a human review gate (amber below). The gates are where the engineering happens.

  1. 01 · SpecStories to technical specUSER_STORIES.md → SPEC.mdYou check: every AC traced, no open decisions
  2. 02 · ContextWrite project rulescopilot-instructions.mdYou check: stack and conventions are right
  3. 03 · CodeGenerate implementationapp/ · static/You check: read every line, run it
  4. 04 · TestsGenerate tests from ACstests/You check: tests fail when code is wrong
  5. 05 · ContainerGenerate DockerfileDockerfileYou check: builds, runs, non-root
  6. 06 · PipelineGenerate CI/CD config.gitlab-ci.ymlYou check: validates, no secrets in file
  7. 07 · DeployShip to a hostRender (or a VM)You check: health endpoint answers
  8. 08 · IterateFeature branch + MRmerge requestYou check: AI review + your review

Step 8 loops back to Step 1: every new feature starts as a new user story and a spec change, then tests, then code.

STEP 0Set up your tools

Goal: VS Code with Copilot signed in, an empty GitLab project cloned locally.

Install

  • VS Code, then the extensions GitHub Copilot (includes Chat), Microsoft's Python (includes Pylance), Ruff, and Microsoft's Docker / Container Tools extension
  • Python 3.13, Git, and Docker Desktop (or Docker Engine on Linux)

Sign in to Copilot Free

  1. Create or sign in to a GitHub account. Copilot works with any Git host; GitHub is only used to sign in.
  2. In VS Code, open the Accounts menu (bottom-left) and choose Sign in to use Copilot. Choose the free plan when asked.
  3. Open the Chat view (Ctrl+Alt+I, or ⌃+⌘+I on macOS) and send "hello" to confirm it works.

Budget your chat requests

The free plan has monthly limits. At the time of writing it allows about 2,000 code completions and a small chat/agent allowance (reported as about 50 requests a month), with the model picked automatically. GitHub changes these numbers, so check the Copilot status icon in VS Code's status bar for your current usage.

  • This walkthrough uses about 12–18 chat requests. Each prompt card below shows its cost.
  • Write one complete prompt instead of five short follow-ups.
  • Use inline completions (cheap) for small edits; save chat for whole files and reviews.
  • Verified students can apply through GitHub Education for the Copilot Student plan, which has higher limits.

Create the GitLab project

  1. On GitLab.com: New project → Create blank project. Name it tasktrack, untick "Initialize repository with a README".
  2. Add your SSH key under User settings → SSH Keys if you have not already.
  3. New GitLab.com accounts must verify their identity before pipelines can use the shared (instance) runners. Do this now so Step 6 does not stall.

STEP 1From user stories to a specification

Goal: a reviewed SPEC.md that settles every design decision, so the code, tests and pipeline can be built from it without guessing.

On a real team you rarely start from a blank page. A product owner hands you user stories with acceptance criteria, and the team's architect turns them into a technical specification. In this step Copilot plays the architect and you review its work.

1a · Start from the user stories

User stories describe what users need, in their words. They say nothing about HTTP, JSON or data structures. Those are design decisions, and they belong in the spec.

The user story saysThe spec must decide
"I am told the title is required" (AC-1.4)Which status code, which JSON error shape, which field name in the error
"It appears in my list with a task number" (AC-1.1)How ids are generated, their type, where they start
"The new task never gets the deleted task's number" (AC-3.3)Whether the id counter ever goes down, and how the store keeps it
"I am told which task was deleted" (AC-3.1)Whether DELETE returns the deleted task (200) or nothing (204)
"Lost on restart is acceptable" (product owner note)An in-memory store, with its structure, invariants and limits

For this tutorial, assume the product owner has already written these stories. Create USER_STORIES.md in your project and paste them in:

1b · Ask Copilot to act as a senior software architect

A vague prompt such as "write a spec for a to-do app" gets a vague spec back. An architect-level prompt has five parts, and each one removes guesswork:

Part of the promptWhy it is there
Role: "You are a senior software architect"Asks for decisions and their reasons, not a feature list
Input: #file:USER_STORIES.mdThe spec is derived from the stories, not invented
Fixed constraints: stack, endpoints, status codesDecisions already made by the team; the AI must not change them
Required sections, numberedForces coverage of endpoints, JSON schemas, status codes, the data store and traceability
Rules: no TBDs, every AC tracedMakes the result usable as an implementation reference

Open Chat in Ask mode and send this prompt. Typing # in the chat box lets you pick the file to attach.

Copy the answer into a new file SPEC.md. Long answers are sometimes cut off; if that happens, reply "Continue from section N" instead of repeating the whole prompt.

1c · Review it as a second architect

Spend one more request making the AI check the draft against the stories. Models are better at finding problems in a document than at avoiding them while writing it.

Accept the findings you agree with and edit SPEC.md by hand. Where the two "architects" disagree, you make the call; you are the one who will implement it.

1d · The reviewed specification

Your spec will differ in wording. Use this reviewed version for the rest of the tutorial, so your code, tests and pipeline match the reference solution.

Every later step builds directly on one section of this spec:

Spec sectionBecomesStep
2 · Design decisionsProject rules in copilot-instructions.md, review checklists2, 3, 8
3 · EndpointsRoutes in app/main.py3
4 · Payload schemasPydantic models in app/models.py3
5 · Status codes and errorsException handlers in app/main.py, error assertions in tests3, 4
6 · In-memory data storeapp/store.py3
7 · Non-functional requirementsCoverage threshold, Dockerfile, pipeline2, 5, 6
8 · Traceability matrixTest names in tests/test_tasks.py4

Review gate: spec

  • Coverage. Every acceptance criterion in USER_STORIES.md has a row in the traceability matrix.
  • Exact rules. Limits are numbers (1–100 characters, not "a reasonable length"); every endpoint lists every status code it can return.
  • 400 vs 422. The rule is stated once (D-7) and every example follows it. FastAPI on its own returns 422 for malformed JSON, so this is a decision the code will have to implement on purpose.
  • Schemas. Every JSON example in section 3 is valid against the schemas in section 4. Paste a schema and an example into a JSON Schema validator website if you are unsure.
  • Store. The structure, the id rule after deletes, and the lock are written down, not left to the implementer.
  • Scope. There is an explicit out-of-scope list. AI drafts like to add pagination, auth and PUT endpoints nobody asked for.
  • Would a classmate build the same thing from this document?

STEP 2Give Copilot project context

Goal: Copilot follows your stack and conventions without you repeating them in every prompt.

VS Code automatically adds the file .github/copilot-instructions.md to every chat request in this workspace. It works the same whether your repository is on GitHub or GitLab. Keep it short and factual. The most useful lines repeat the design decisions where the spec disagrees with FastAPI's defaults, because those are the ones the AI gets wrong.

Also start an AI usage log. Your instructor may require it, and it is good practice for any team that needs to know where code came from.

Pin the dependencies before any code exists, so the AI writes against real versions. Runtime packages go in requirements.txt (these ship in the Docker image); tools for development and CI go in requirements-dev.txt.

Create a virtual environment, select it in VS Code (Python: Select Interpreter from the Command Palette, Ctrl+Shift+P), and install:

pyproject.toml holds the pytest and Ruff settings. --cov-fail-under=80 makes the test run fail if line coverage drops under 80% (NFR-4). The Ruff rule set includes S (security checks from Bandit) and B (common bug patterns).

STEP 3Generate the code

Goal: a working backend and frontend that you have read line by line.

3a · Scaffold the backend with Agent mode

Switch the Chat view to Agent. Agent mode can create files, so tell it exactly which files to create and what not to touch. A narrow prompt gives you a smaller diff to review.

The agent shows each file it creates or edits. Read the diff before you click Keep; click Undo for anything you do not understand and ask about it in Ask mode instead.

Check each file against the spec section it implements. The models are SPEC section 4 written in Pydantic: the JSON Schema limits (minLength, maxLength, enum, additionalProperties: false) map to StringConstraints, Priority and extra="forbid". Pydantic checks every request body before your route function runs, so the routes stay short.

The store is SPEC section 6: a dict keyed by id, a counter that only goes up (D-4), and a lock around every access (D-12).

The two exception handlers in create_app exist because the spec disagrees with FastAPI's defaults. FastAPI reports every input problem, including malformed JSON, as 422 with a {"detail": [...]} list. SPEC section 5 asks for 400 for malformed JSON (D-7) and the {"error": {...}} envelope for everything. Copilot will usually follow the framework rather than your spec unless the prompt points this out.

3b · Write the frontend with inline completions

For smaller files, inline completions are cheaper and keep you in control. Type a descriptive comment and a function signature, pause, and Copilot proposes the body. Tab accepts, Esc rejects, Alt+] (⌥+] on macOS) shows the next alternative, and Ctrl+→ (⌘+→) accepts one word at a time. The same works in Python files: type a def line and a docstring, then pause.

If you prefer to spend a chat request, this prompt produces both files at once:

3c · Run it

Compare each response with the examples in SPEC sections 3 and 5.2; they should match apart from ids and timestamps. Then open /docs. FastAPI generates it from your code, so it is an independent view of what you actually built: the endpoint table in SPEC section 3 and the routes listed in /docs should match one to one, including the 400, 404 and 422 responses with the ErrorResponse schema.

Review gate: code. What AI-generated code often gets wrong here

  • XSS. Writing titles with innerHTML. Try adding the task <img src=x onerror=alert(1)>. With textContent it shows as plain text.
  • Framework defaults vs. the spec. 422 for malformed JSON instead of 400 (D-7); {"detail": ...} instead of the SPEC 5.2 envelope; 204 for DELETE where the spec says 200 with the task (D-9); 200 for POST instead of 201.
  • Paths. An /api prefix, or /tasks/{task_id} in the URL, because that is common in examples. The spec says /tasks/{id}.
  • Silent coercion and ignored fields. Without strict=True, Pydantic turns 42 into "42"; without extra="forbid", it silently drops unknown fields. Both break D-6. Try them with curl.
  • The id rule. id = len(tasks) + 1 looks right and reuses ids after a delete, which breaks AC-3.3 and can overwrite a task.
  • The lock. A store without threading.Lock works in every manual test and still breaks D-12 under load. Tests rarely catch this; review must.
  • Old library versions. Pydantic v1 code (@validator, .dict(), class Config) still appears in suggestions. Use v2 (StringConstraints, model_dump(), ConfigDict).
  • Shared state. A module-level store makes tests leak data into each other. The create_app(store) factory lets every test start empty (D-13).
  • Route order. Mounting the static files at / before the API routes hides the API. The mount must come last.
  • Invented packages. If the AI imports a package you did not install, check it exists on pypi.org, who publishes it and when it was last released before you install it.

Rule of thumb: if you cannot explain a line to a classmate, you are not ready to commit it.

STEP 4Generate the tests

Goal: one test per row of the spec's traceability matrix, plus edge cases, with coverage over 80%.

Generate tests from the spec, not just from the code. If you only say "write tests for main.py", the AI tends to encode whatever the code currently does, bugs included. The traceability matrix in SPEC section 8 already names every test, so the prompt can ask for exactly those. The /tests command tells Copilot you want test code.

FastAPI's TestClient calls the app in memory, with no server running. It depends on the httpx2 package. Older examples, and AI suggestions trained on them, install httpx instead, which now produces a deprecation warning.

The API tests follow the user stories. Notice that they check the whole error envelope, not only the status code: a 422 with the wrong shape still breaks the web page.

Test the tests

Passing tests prove little if they would also pass against broken code. Introduce a bug on purpose, run the tests, and confirm something fails. This is manual mutation testing. Every row below was run against the reference solution.

Mutation (change, run, then revert)Result
In models.py, Title: set strip_whitespace=FalseCaught by AC-1.3, AC-1.4 [spaces-only] and two unit tests
In main.py: replace the json_invalid check with if False:Caught by test_d7_malformed_json_returns_400
In main.py: remove status_code=201 from the POST routeCaught by AC-1.1 and every test that adds a task
In models.py: remove extra="forbid"Caught by test_d6_rejects_invalid_bodies[unknown-field]
In store.py: replace self._next_id += 1 with self._next_id = len(self._tasks) + 1Caught by AC-3.3, but only because that test deletes from the middle and then adds twice (see below)
In store.py, add: replace with self._lock: with if True:Not caught. All tests still pass.

The last two rows are the interesting ones. The first version of the AC-3.3 test was "add, delete, add, check the id is 2". The len(self._tasks) + 1 bug passes that test and then overwrites a task on the next add. The fix was a stronger test, not more tests. The missing lock is never caught, because a race condition needs exact timing that tests almost never produce. That is why D-12 is written in the spec and checked in code review rather than left to the test suite.

Review gate: tests

  • Does every row of the SPEC section 8 matrix have a test with that exact name? (pytest -v lists them.)
  • Does each test assert something specific (status and body), not just "no error"?
  • Did every mutation above behave as the table says? If a "caught" row passes for you, your test is weaker than the reference one.
  • Coverage tells you which lines ran, not whether they are correct. This suite reaches 100% and still cannot detect the missing lock.

STEP 5Containerize

Goal: a small, non-root image that passes its health check.

The slim Python image has no curl or wget, so the health check is a few lines of standard-library Python. A common AI mistake is a HEALTHCHECK that calls curl: the container then reports "unhealthy" forever even though the app works.

Review gate: container

  • Run docker run --rm tasktrack:local whoami: it should print appuser, not root.
  • Only requirements.txt is installed in the image. pytest and Ruff belong in requirements-dev.txt and must not ship.
  • Tests, the .venv folder, coverage files and .env must not end up in the image. Check the .dockerignore.
  • Check the runtime dependencies for known vulnerabilities: pip install pip-audit, then pip-audit -r requirements.txt.

STEP 6Build the CI/CD pipeline

Goal: every push is linted and tested; every push to main also builds and publishes an image.

lint→ test→ build→ deploy (manual)

Pipeline YAML is where AI assistants make the most confident mistakes: outdated keywords, made-up variables, or secrets typed straight into the file. Name the predefined variables you expect and forbid hard-coded secrets in the prompt.

JobRuns onWhat it proves
lintevery pushCode passes the Ruff rules (including its security checks) and is formatted
testevery pushAll tests pass and coverage ≥ 80%; results appear in the merge request
buildmain onlyThe image builds, starts and answers /health before it is pushed
deploymain, manualThe hosting service took the new image and the live app is healthy

Review gate: pipeline

  • Open Build → Pipeline editor in GitLab and paste the file. It validates the syntax before you commit.
  • Every $VARIABLE is either predefined by GitLab (CI_REGISTRY, CI_COMMIT_SHORT_SHA, …) or one you will create in Step 7. Look up any you do not recognize in GitLab's predefined-variables reference.
  • If the AI used only: / except:, ask it to rewrite them as rules:, the current GitLab keyword.
  • No tokens, passwords or URLs with keys appear anywhere in the file.

In GitLab, open Build → Pipelines. The first run takes a few minutes. When it is green, open the test job's Tests tab to see each test, and Deploy → Container registry to see your image tagged with the commit hash and latest. The deploy job waits for you; you will set it up next.

STEP 7Deploy

Goal: a public URL serving the image your pipeline built.

This walkthrough uses Render, which can run a container image from GitLab's registry on a free instance. Free instances go to sleep when idle, so the first request after a break can take up to a minute. Check Render's current free-tier terms before you rely on it. If your course provides a Linux VM, use the alternative at the end of this step.

7a · Let Render pull your image

  1. In GitLab: Settings → Repository → Deploy tokens → Add token. Name it render, tick only read_registry, and create it. Copy the username and token; GitLab shows the token once.
  2. In Render: New → Web Service → Existing image. Image URL: registry.gitlab.com/<your-username>/tasktrack:latest (all lowercase). Add a registry credential for registry.gitlab.com with the deploy-token username and token.
  3. Choose the Free instance type, set the health check path to /health, and create the service. Render sets PORT for you; the image's start command already reads it.
  4. Copy the service URL (for example https://tasktrack-xxxx.onrender.com) and, from the service's Settings → Deploy hook, the deploy hook URL. The hook URL contains a secret key.

7b · Give the pipeline its two variables

In GitLab: Settings → CI/CD → Variables → Add variable.

KeyValueFlags
RENDER_DEPLOY_HOOK_URLThe deploy hook URLProtect. Also Mask if GitLab accepts the value; if it rejects masking because of characters in the URL, keep it protected and never print it in a job.
APP_URLYour service URL, no trailing slashProtect

"Protected" variables are only available to pipelines on protected branches such as main, so a feature branch cannot trigger a production deploy.

7c · Deploy

Open the latest main pipeline and press the play button on deploy. The job calls the hook, then polls /health for up to five minutes. When it passes, Operate → Environments → production links to your live app.

Review gate: deployment

  • Open the live URL, add a task, refresh. It is still there until the instance restarts; that is the in-memory store doing what the spec says (persistence is out of scope).
  • curl -s $APP_URL/health returns {"status":"ok",…}.
  • Search the job log for your hook key. It must not appear.

Alternative: deploy to a course VM over SSH

If you have a Linux VM with Docker, replace the deploy job with this one. Create CI/CD variables SSH_PRIVATE_KEY (protected), SSH_KNOWN_HOSTS (output of ssh-keyscan your-vm), DEPLOY_HOST and DEPLOY_USER. The job token used to log in to the registry expires when the job ends, so no long-lived registry password is stored on the VM.

STEP 8Iterate with merge requests

Goal: add a feature the way a team would: new story, spec change, failing tests, code, review, merge.

The product owner has a new story for release 1.1: US-4, mark a task as done. It needs a new endpoint (PATCH /tasks/{id}), a new field in the Task schema, and a new store operation, so it touches every section of the spec. Work on a branch so the pipeline checks your change before it reaches main.

1 · Story and spec change first

Add the US-4 story from the prompt below to USER_STORIES.md. Then ask the architect for the spec change only:

Before you accept the proposal, make sure it answers these questions. Each is a decision a developer would otherwise make silently in the code:

  • Is the PATCH body {"done": true} only, or can it also change the title? Is {} a 422?
  • Is {"done": "true"} rejected with 422, as D-6 requires?
  • May POST /tasks include "done", or is it still an unknown field (AC-4.3)?
  • Does PATCH return 200 with the updated task, like DELETE returns the deleted one?
  • Does the new store operation take the lock (D-12)?
  • Which rows are added to the traceability matrix, and what are the test names?

Edit the proposal until you agree with it, update SPEC.md, and commit the two documents on their own. The spec change is reviewed before any code exists.

2 · Failing tests, then code

Ask Copilot for the new test_ac4_* tests only, using the names from the new matrix rows. Run pytest and watch them fail for the right reason: PATCH /tasks/1 returns 405, because the route does not exist yet. A test that fails for some other reason, such as an import error, is not testing the feature.

Then ask Agent mode to implement the spec change: done in the Task model, a TaskUpdate model, an update operation in the store, the route in app/main.py, and a checkbox in static/. Run the tests until they pass, then ruff check . and ruff format ..

3 · AI review, then your review

Before committing, ask for a review of your uncommitted changes. #changes attaches your current Git diff.

In the Source Control view, the sparkle button next to the message box drafts a commit message from your staged diff. Edit it to follow your team's format, e.g. feat: mark tasks as done (US-4).

4 · Merge request

  1. Open the merge request. The branch pipeline runs lint and test; test results show in the MR.
  2. Ask a classmate to review. Mention in the description which parts were AI-generated, and paste the relevant PROMPTS.md rows.
  3. Merge. The main pipeline builds a new image; press play on deploy and check the live app.

Using AI responsibly

ConcernWhat you do
OwnershipYou are the author of everything you commit. Read the diff, run it, and be able to explain it.
VerificationTrust tests, linters, the pipeline and the documentation over the AI's confidence. AI explanations can sound right and be wrong.
SecretsNever paste tokens, keys or .env contents into chat. Keep secrets in protected CI/CD variables and .env in .gitignore.
DependenciesAI tools sometimes suggest packages that do not exist; attackers register look-alike names. Verify every new dependency before installing it.
LicensingIn your GitHub account's Copilot settings you can block suggestions that match public code. Ask your instructor which setting the course expects.
PrivacyYour prompts and code context are sent to an external service. Do not use it with code or data you are not allowed to share.
Academic integrityFollow your course policy. Keep PROMPTS.md current; it shows your judgment, which is what is being assessed.

Troubleshooting

SymptomLikely cause and fix
Pipeline stuck in "pending"No runner available. Complete GitLab identity verification, and check Settings → CI/CD → Runners has instance runners enabled.
pip install fails in CI: no matching versionA pinned version does not exist for Python 3.13, or the AI invented a version number. Check the package on pypi.org and fix the pin.
ModuleNotFoundError: No module named 'app'Run pytest and uvicorn from the project root, and keep pythonpath = ["."] in pyproject.toml.
VS Code underlines every import, or pytest is not foundThe virtual environment is not active or not selected. Run Python: Select Interpreter and choose .venv; open a new terminal.
Tests pass locally, fail in CIDifferent Python version or an unpinned package. Run them in the CI image: docker run --rm -v "$PWD":/app -w /app python:3.13-slim sh -c "pip install -r requirements-dev.txt && pytest"
lint fails on ruff format --checkCode was not formatted locally. Run ruff format . and commit. Turning on "format on save" with the Ruff extension prevents this.
Container keeps reporting "unhealthy"The HEALTHCHECK calls a tool that is not in the image (curl, wget) or the wrong port. Check with docker inspect --format '{{json .State.Health}}' tasktrack.
build: cannot connect to the Docker daemonThe docker:27-dind service or DOCKER_TLS_CERTDIR is missing from the job.
Push to registry deniedThe container registry is turned off: Settings → General → Visibility, project features, permissions.
Render cannot pull the imageDeploy token lacks read_registry, or the image path has capital letters.
deploy health check times outFree-instance cold start or a failed Render deploy. Check Render's deploy log; raise --retry if it is only slow.
deploy runs with an empty URLThe variables are protected but the branch is not. Deploy only from main.
Copilot says you reached your limitMonthly allowance used. Continue with inline completions or by hand, wait for the reset, or apply for the Student plan.

Exercises

  1. Due dates. Write a user story with acceptance criteria for an optional due date, then go through the full loop: architect prompt for the spec change, failing tests, code, MR. Which decisions (format, time zone, past dates, sort order) did the architect make that the story never mentioned?
  2. Spec without an architect. In a new chat, ask Copilot for "a spec for a FastAPI to-do API" with no stories, constraints or required sections. Compare it with your SPEC.md: list the design decisions it left open or got different, and which of your tests its version would fail.
  3. Contract test. Install jsonschema as a dev dependency and write a test that validates real API responses against the JSON Schemas in SPEC section 4. Should the schemas then move into their own files so both the spec and the test use them?
  4. Security stage. Add a pipeline job that runs pip-audit -r requirements.txt and fails the pipeline when a runtime dependency has a known vulnerability. Where in the stage order should it go, and why?
  5. Persistence. Replace TaskStore with a SQLite-backed store (Python's built-in sqlite3 module) behind the same methods. Which tests needed to change, and what does that tell you about the design?
  6. Reflection (one page). Using your PROMPTS.md, describe three suggestions you rejected and why. Where did AI save the most time, and where did it cost you time?
