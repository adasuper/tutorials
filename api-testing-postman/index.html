Testing a CRUD API with Postman

You will turn CRUD test cases into automated tests in Postman, prove they pass on a correct build of a Student Enrollment API, then use the same tests to find defects in a new build.

  • Tools Postman desktop app · Python 3.7+
  • Technique Black-box API testing · CRUD · regression testing
  • Time about 1 hour

Who this tutorial is for

Undergraduate software engineering students who have designed test cases on paper and want to automate them. You will practise black-box testing of a REST API: checking status codes, response bodies and postconditions, and using one test suite against two builds to catch regressions.

What you will have at the end

  • A Postman collection with automated tests for Create, Read, Update and Delete, each checking status, body and postconditions
  • Proof that every test passes on the correct build
  • A defect log for the release-candidate build, with the evidence for each defect

The API under test

The tutorial uses two builds of the same Student Enrollment API. Both run on your own computer:

BuildAddressWhat it is
1.0http://localhost:3000Released build. It works correctly.
1.1http://localhost:3001Release candidate. It may contain defects. Your job is to find them.

Black-box testing

Test the API only through Postman. Do not open or read the server code. Your expected results come from the specification below, not from the implementation.

Files you need

Download both starter files and save them in one folder, such as crud-lab:

  • student_api.py: the API server, which runs both builds. It uses only the Python standard library, so there is nothing else to install.
  • CRUD-Lab-Starter.postman_collection.json: a Postman collection with a reset request and one worked example

If your browser opens a file instead of saving it, right-click the link and choose Save link as. Keep the file names exactly as shown.

Specification

ReadGET /students/{id}200404, 400
UpdatePUT /students/{id}200404, 400
DeleteDELETE /students/{id}200404, 400

A student is {"id": 1–9999, "name": 1–40 characters, "age": 16–120}.

  • Invalid input or malformed JSON returns 400.
  • Creating an id that already exists returns 409.
  • GET, PUT or DELETE on a student that does not exist returns 404.
  • A PUT body needs name and age; id is optional but must match the URL.

After every reset the data is: 1001 Alice 20, 1002 Bob 22, 1003 Chen 19.

STEP 1Install Python and Postman

Goal: Python 3.7 or newer, and the Postman desktop app signed in with a free account.

  1. Check Python. Open a terminal and run the command below. On Windows also try py --version; on macOS try python3 --version. If you see Python 3.x.y with x of 7 or higher, you are done with this step. Remember which command worked (python, py or python3).
  1. Install Postman. Download the desktop app from postman.com/downloads and install it.
  2. Sign in. Open Postman and create a free account or sign in. Skip any tour or team setup.
  3. Find your workspace. After sign-in you land in a workspace (usually My Workspace). The left sidebar lists Collections. That is where your tests will live.

Use the desktop app

Postman in a web browser cannot reach localhost on your computer without an extra helper (the Postman Desktop Agent). The desktop app works out of the box.

Goal: understand how a Postman test reads a response, passes, and fails.

  1. Reset the data. Open 0 Setup → Reset test data and click Send. The response pane should show 200 OK and a body like {"message": "data reset", "count": 3}. Send this request at the start of every test run, so every run starts from the same data.
  2. Open the worked example. Open 1 Create → C-ex Create student with invalid age (15). It is a test case for the lower age boundary, automated.

Each pm.test("name", function) is one check; the name is what you see in the results. Inside, pm.response is the response that came back, pm.response.json() turns its body into a JavaScript object, and pm.expect(...) states what must be true. If any line inside a pm.test fails, that check fails.

  1. Send it. Click Send. The status is 400 Bad Request and the body is {"error": "age must be an integer from 16 to 120"}.
  2. Read the results. Click Test Results in the response pane. You should see two green PASS lines.
  3. See a failure on purpose. In the script, change 400 to 201 and click Send again. The first check now shows a red FAIL with a message like expected response to have status code 201 but got 400. Change it back to 400 and save.
  4. Check the postcondition. Open C-ex (postcondition) No student 2001 was created and send it. It sends GET {{baseUrl}}/students/2001 and expects 404, proving the rejected student was not stored.

Why postconditions matter

A response only tells you what the server said. A follow-up request tells you what it actually did. Checking postconditions this way is how you verify the data really changed (or didn't).

STEP 5Write your own tests

Goal: at least two automated test cases for each of Create, Read, Update and Delete.

One test case is one request, plus a follow-up request when you check a postcondition. If you have already designed test cases on paper, automate those. If not, start from the ideas in 5.3.

5.1 · Add a request to a folder

  1. In the sidebar, hover over a folder (for example 1 Create), click the … (View more actions) that appears, and choose Add request.
  2. A request named New Request opens. Click its name at the top of the tab and rename it after your test case, for example C1 Create valid student.
  3. Pick the method from the dropdown and type the URL, always starting with {{baseUrl}}. The variable turns orange or green when Postman recognizes it.
  4. For POST and PUT: click Body, choose raw, then choose JSON in the dropdown at the right end of that row (it may say Text at first). Type the JSON input.
  5. Click Scripts → Post-response and write the checks (see 5.2).
  6. Save, then click Send and read Test Results.

Shortcut: right-click an existing request and choose Duplicate, then rename it and drag it into the right folder. The Snippets list beside the script editor also helps: clicking Status code: Code is 200 inserts a ready-made status check you can edit.

Test ideas taken from the specification. Each covers a valid case, a boundary or an error path:

OperationInputExpected
CreateAn id that already exists, such as 1001409; student 1001 unchanged
CreateA name of exactly 40 characters, then 41201, then 400
ReadStudent 1001200; body is Alice, 20
ReadAn id that does not exist, such as 9999404
UpdateStudent 1003 with a new name and age200; a follow-up GET shows the new values
UpdateStudent 1003 with an id in the body that does not match the URL400; student 1003 unchanged
DeleteStudent 1002200; a follow-up GET returns 404
DeleteAn id that does not exist404

Keep tests from stepping on each other

Requests run top to bottom, and some change data. A simple plan:

  • Create tests use new ids (2010, 2011, …).
  • Read tests use 1001 and an id that does not exist.
  • Update tests use 1003.
  • Delete tests use 1002 and come last.

Then a Delete never removes a student that a later Read expects.

Write each test to the spec, not to what you see

Decide the expected result from the specification before you click Send. If build 1.0 disagrees, recheck the specification and your test first; build 1.0 is known to be correct.

STEP 6Make everything pass on build 1.0

Goal: every check green on the correct build, so a red check later means a defect, not a bad test.

  1. Send Reset test data.
  2. Send every request in order, top to bottom: 1 Create, 2 Read, 3 Update, 4 Delete.
  3. Every check must be green. Build 1.0 is correct, so a red check on 1.0 means the test is wrong: a typo in the URL, a wrong expected value, a missing JSON setting on the body, or an earlier request that changed the data. Fix it, save, reset and rerun.

Optional: run the whole collection at once

Click the collection name, then Run (or … → Run collection). The Collection Runner lists all requests with checkboxes in their run order; click the orange Run button. It sends every request and shows pass or fail per request. Your Postman plan may limit how many Runner runs you get per month, so sending requests one by one is always a safe fallback.

STEP 7Hunt defects in build 1.1

Goal: run the same tests, unchanged, against the release candidate and log every failure.

7a · Switch to build 1.1

  1. Click the collection name, then Variables.
  2. Change baseUrl to http://localhost:3001 (both columns if you see two), and save.
  3. Send Reset test data. This resets build 1.1's data, which is separate from build 1.0's.
  4. Send every request again, in the same order, without changing any test.

7b · Log every failure

On build 1.1, each red check points to a candidate defect, because the same test passed on the correct build. For each one, look at the response status and Body, and the server window's log line, and write down:

#Test (request and input)ExpectedActual on build 1.1Checks that failed

A good defect entry

  • Someone else can reproduce it from the request and input alone.
  • The expected result cites the specification, not your opinion.
  • The actual result is copied from the response, not paraphrased.

STEP 8Export and wrap up

Goal: a clean, shareable copy of your test suite.

  1. Set baseUrl back to http://localhost:3000 and save, so whoever opens your collection starts on the correct build.
  2. Export the collection. In the sidebar, hover over your collection, click …, and choose More → Export. Save the .postman_collection.json file somewhere safe, or commit it to a Git repository next to the code it tests, so teammates can import and rerun your tests.
  3. Stop the server with Ctrl+C in its terminal window.

Assertion cheat sheet

All lines go inside pm.test("name", () => { ... }); in Scripts → Post-response. Start with const body = pm.response.json(); when you check the body.

To check that…Write
the status code is 201pm.response.to.have.status(201);
the whole body equals an objectpm.expect(body).to.eql({ id: 1001, name: "Alice", age: 20 });
one field has a valuepm.expect(body.name).to.eql("Alice");
a field is a numberpm.expect(body.age).to.be.a("number");
a field is a stringpm.expect(body.name).to.be.a("string");
a string has a lengthpm.expect(body.name).to.have.lengthOf(40);
an error message mentions a wordpm.expect(body.error).to.include("age");
the body has a fieldpm.expect(body).to.have.property("id");
a value is one of severalpm.expect(pm.response.code).to.be.oneOf([200, 201]);
